# مشخصات فنی A10: اعضای تیم، نقش‌ها و دستگاه‌ها

> وضعیت: **تأییدشده (Person A).** تغییرهای لازم در کد Track B و Track C هم در همین تسک انجام می‌شود. این سند جای بخش A10 در [TRACK-A.md](../TRACK-A.md) را در جزئیات می‌گیرد. سقف دستگاه از [A9-billing.md](./A9-billing.md) (بخش ۳) می‌آید.

## ۱. نقش‌ها

| | مالک (`OWNER`) | اپراتور (`OPERATOR`) |
|---|---|---|
| محصولات، موجودی، مشتریان | ✓ | ✓ |
| سفارش‌ها و لینک‌های خرید (با قیمت سفارش) | ✓ | ✓ |
| گزارش فروش: تعداد سفارش، تعداد اقلام، پرفروش‌ها | ✓ | ✓ |
| **اطلاعات مالی:** جمع فروش به تومان، میانگین، درآمد هر کالا، نمودار مبلغ، «فروش امروز» داشبورد | ✓ | ✗ |
| تنظیمات فروشگاه، پرداخت، اشتراک، اعضا، خروجی داده | ✓ | ✗ |

- **یک مالک در هر فروشگاه:** همان کسی که فروشگاه را ساخته و اشتراک را می‌خرد. قابل حذف نیست. اعضای بعدی را فقط او اضافه یا حذف می‌کند. انتقال مالکیت بعداً.
- **کنترل روی سرور:** صفحه‌ها و اکشن‌های فقط‌مالک برای اپراتور ۴۰۴ می‌دهند (`notFound()`). پنهان کردن منو فقط برای راحتی است، نه امنیت.
- قیمت هر سفارش برای اپراتور دیده می‌شود، چون برای ثبت و پیگیری سفارش لازم است. فقط جمع‌ها و گزارش‌های مالی پنهان‌اند.

## ۲. نشست در دیتابیس

جدول جدید:

```prisma
model Session {
  id         String    @id @default(cuid())
  userId     String
  sellerId   String
  createdAt  DateTime  @default(now())
  lastSeenAt DateTime  @default(now())
  userAgent  String?   // برای نمایش «کروم روی اندروید»، کوتاه‌شده
  revokedAt  DateTime?
  @@index([sellerId, revokedAt])
  @@index([userId, revokedAt])
}
```

- کوکی (همان JWT امضاشده) حالا `{ sid, userId, sellerId }` دارد. proxy مثل قبل فقط امضا را بررسی می‌کند.
- **`requireSeller()`** ردیف نشست را می‌خواند: باطل‌شده یا عضویتِ حذف‌شده یعنی رفتن به `/logout`. **خروجی‌اش همان قبلی است**، پس کد Track B عوض نمی‌شود.
- **`requireMember()`** همان به‌علاوهٔ `userId` و `role`. **`requireOwner()`** برای اپراتور `notFound()` می‌کند.
- `lastSeenAt` حداکثر هر ۵ دقیقه یک بار به‌روز می‌شود تا هر درخواست یک نوشتن نداشته باشد.
- **کوکی قدیمی** (فقط `sellerId`): یک بار به `/logout` می‌رود و کاربر دوباره وارد می‌شود.
- خروج (`logoutAction`) نشست را در دیتابیس هم باطل می‌کند.

## ۳. ورود

1. کد پیامکی درست بود → `User` با همان شماره (اگر نبود ساخته می‌شود).
2. **عضویت‌ها:**
   - **هیچ عضویتی ندارد:** مثل قبل فروشگاه تازه ساخته می‌شود و او مالک است (دورهٔ آزمایشی طبق A9، یک بار برای هر شماره).
   - **یک عضویت:** مستقیم وارد همان فروشگاه.
   - **چند عضویت:** صفحهٔ `/select-store` برای انتخاب فروشگاه.
3. سقف دستگاه (بخش ۵) بررسی می‌شود و نشست ساخته می‌شود.

**رفع اشکال مهم:** الان هر ورود با شمارهٔ تازه یک فروشگاه می‌سازد. با این طرح، کارمند دعوت‌شده مستقیم وارد فروشگاه مالک می‌شود، فروشگاه خالی برایش ساخته نمی‌شود و دورهٔ آزمایشی شماره‌اش مصرف نمی‌شود.

**تغییر فروشگاه:** در منوی کناری، برای کسی که بیش از یک عضویت دارد، «تغییر فروشگاه» → `/select-store`. انتخاب فروشگاه نشست فعلی را باطل می‌کند و یک نشست تازه برای فروشگاه دیگر می‌سازد، با همان بررسی سقف دستگاه.

## ۴. دعوت و حذف (`/settings/team`، فقط مالک)
- **دعوت:** مالک شمارهٔ موبایل را وارد می‌کند (و نقش همیشه `OPERATOR` است).
  - سقف اعضا با `canUse(sellerId, "addMember")` کنترل می‌شود، در یک تراکنش با قفل ردیف `Subscription`، مثل سقف کالا.
  - عضویت فوراً ساخته می‌شود، بدون مرحلهٔ پذیرفتن. پیامک `MEMBER_INVITE` با نام فروشگاه فرستاده می‌شود (بعد از commit). شکست پیامک دعوت را خراب نمی‌کند.
  - شمارهٔ تکراری یا شمارهٔ خود مالک: خطای فرم.
- **فهرست اعضا:** شماره (ماسک‌شده برای دیگران نیست؛ مالک باید ببیند)، نقش، تاریخ عضویت، تعداد دستگاه‌های فعال.
- **حذف عضو:** عضویت حذف و همهٔ نشست‌های او در این فروشگاه باطل می‌شوند؛ در درخواست بعدی بیرون می‌رود. مالک قابل حذف نیست.
- **«خروج از همهٔ دستگاه‌ها»** برای هر عضو (مالک برای همه).

## ۵. دستگاه‌ها

**سقف‌ها** (از `plans.ts`): پلن رایگان کل فروشگاه ۱ دستگاه؛ بقیه و دورهٔ آزمایشی ۲ دستگاه برای هر عضو.

- **هنگام ورود بیش از سقف:** ورود رد نمی‌شود؛ قدیمی‌ترین نشست همان نفر (با `lastSeenAt`) باطل می‌شود.
- **وقتی پلن تمام شد و فروشگاه روی رایگان رفت** (تصمیم Person A): فقط **یک دستگاه مالک** — آخرین نشست فعالش — می‌ماند و همهٔ نشست‌های دیگر **فوراً** باطل می‌شوند، در اولین درخواستی که این را ببیند. اپراتورها روی پلن رایگان نمی‌توانند وارد شوند (پیام: «اشتراک فروشگاه تمام شده است. به مالک فروشگاه اطلاع دهید.»)، ولی عضویتشان پاک نمی‌شود و بعد از تمدید دوباره وارد می‌شوند.
- این بررسی در `requireSeller()` است ولی فقط وقتی وضعیت مؤثر `FREE` است و `enforced` (یعنی `BILLING_ENABLED` روشن) یک کوئری اضافه دارد.
- با `BILLING_ENABLED=false` هیچ سقف دستگاهی اعمال نمی‌شود، مثل بقیهٔ سقف‌ها.

**`/settings/devices`** (برای همه، هم مالک هم اپراتور، فقط دستگاه‌های خودش): فهرست نشست‌های فعال (نوع دستگاه، آخرین استفاده، «این دستگاه») و دکمهٔ «خروج» برای هر کدام و «خروج از همهٔ دستگاه‌های دیگر». این تنها تب تنظیمات است که اپراتور می‌بیند.

## ۶. تغییرات در کد دیگران
- **Track B:** گزارش فروش (`/reports`) برای اپراتور مبلغ‌ها را نشان نمی‌دهد. تب «پرداخت» (`/settings/payments`) و اکشن‌هایش فقط مالک.
- **Track C:** «فروش امروز» در خلاصهٔ داشبورد (C5) برای اپراتور نشان داده نمی‌شود. `requireMember()` برای خروجی داده (C6) آماده است.
- هر تغییر در فایل‌های تیم‌های دیگر کوچک است و در PR فهرست می‌شود.

## ۷. تست
- **دیتابیس:**
  - عضو یک فروشگاه به دادهٔ فروشگاه دیگر دسترسی ندارد.
  - عضو حذف‌شده و نشست باطل‌شده در درخواست بعدی رد می‌شوند.
  - دعوت: سقف اعضا، هم‌زمانی دو دعوت، شمارهٔ تکراری.
  - ورود: شمارهٔ دعوت‌شده فروشگاه تازه نمی‌سازد؛ چند عضویت.
  - دستگاه: سومین ورود قدیمی‌ترین را باطل می‌کند؛ افتادن به رایگان فقط یک دستگاه مالک را نگه می‌دارد؛ اپراتور روی رایگان رد می‌شود.
  - کوکی قدیمی.
- **سرور:** اپراتور روی `/settings/billing`، `/settings/team`، `/settings/payments` و اکشن‌هایشان رد می‌شود.
- **e2e:** مالک عضو دعوت می‌کند؛ اپراتور وارد می‌شود، سفارش ثبت می‌کند، مبلغ‌های گزارش را نمی‌بیند و روی `/settings/billing` ۴۰۴ می‌گیرد؛ مالک او را حذف می‌کند و درخواست بعدی اپراتور به صفحهٔ ورود می‌رود.

# استقرار، انتشار، CI و پیامک (Track C)

راهنمای C1 و C3 از [TRACK-C.md](./TRACK-C.md). هدف این است که یک نفر بتواند **فقط با همین فایل** برنامه را از صفر روی پروداکشن بیاورد، نسخهٔ جدید منتشر کند، و در صورت مشکل به نسخهٔ قبل برگردد. پشتیبان‌گیری و بازیابی (C2) در PR خودش به این فایل اضافه می‌شود.

**قانون همیشگی:** هیچ رمز، کلید یا رشتهٔ اتصال دیتابیسی در مخزن، PR، Issue یا پیام ایجنت نیاید. متغیرهای پروداکشن فقط در پنل میزبان تنظیم می‌شوند. هر کار مستقیم روی پروداکشن (مایگریشن، تغییر متغیر، بازیابی) پیش از انجام در یک Issue نوشته می‌شود و نتیجه‌اش همان‌جا ثبت می‌شود (قانون ۳ README فاز ۲).

## ۱. میزبان

### پیشنهاد: لیارا، پلتفرم Docker
بررسی مستندات هر دو میزبان در ۳ مهر ۱۴۰۵. پیوند هر ادعا کنارش است؛ چیزی که در مستندات پیدا نشد «تأییدنشده» است و در فهرست سؤال‌های پشتیبانی آمده.

| معیار (TRACK-C) | لیارا | آروان‌کلود |
|---|---|---|
| Postgres 16 مدیریت‌شده | بله، ۱۳ تا ۱۸ از جمله ۱۶ ([نسخه‌ها](https://docs.liara.ir/dbaas/postgresql/choose-version/)). نسخه بعداً عوض نمی‌شود | تأییدنشده؛ نمونهٔ Terraform نسخهٔ ۱۷ است |
| شبکهٔ خصوصی برنامه و دیتابیس | بله، و دسترسی عمومی دیتابیس خاموش‌شدنی ([شبکهٔ خصوصی](https://docs.liara.ir/paas/details/private-network/)) | تأییدنشده؛ فایروال دیتابیس به‌طور پیش‌فرض همهٔ IPها را می‌پذیرد ([امنیت](https://docs.arvancloud.ir/fa/databases/secure/)) |
| ذخیره‌ساز S3 | بله، با همان تنظیم کد ما: `region: "default"` و path-style ([نمونهٔ Next.js](https://docs.liara.ir/object-storage/how-tos/connect-via-platform/nextjs/)) | بله؛ نسخه‌گذاری رایگان هم دارد |
| انتشار بدون قطعی | بله: ترافیک فقط بعد از سالم بودن نسخهٔ جدید جابه‌جا می‌شود ([zero-downtime](https://docs.liara.ir/paas/details/zero-downtime-deployment/))، **فقط در بستهٔ نقره‌ای و طلایی** | تغییر در پنل «باعث ری‌استارت و قطعی» می‌شود ([مدیریت برنامه](https://docs.arvancloud.ir/fa/cloud-container/manage-app/)) |
| Node 24 | بله (پلتفرم Next.js) و در Docker هر نسخه‌ای | فقط ایمیج Docker |
| HTTPS دامنهٔ اختصاصی | رایگان و تمدید خودکار ([SSL](https://docs.liara.ir/paas/domains/enable-ssl/)) | فقط از راه CDN آروان |
| پرداخت ریالی | کیف پول تومانی | ساعتی تومانی |

**چرا لیارا:** Postgres 16 صریحاً هست، دیتابیس در شبکهٔ خصوصی است، انتشار بدون قطعی با بررسی سلامت دارد، و تنظیم S3 آن با کد فعلی ما یکی است. آروان در پشتیبان‌گیری دیتابیس (PITR) و نسخه‌گذاری فایل قوی‌تر است، ولی انتشار از پنلش قطعی دارد، Postgres 16 تأیید نشد، و دامنهٔ اختصاصی CDN آن را اجباری می‌کند (یک پراکسی بیشتر جلوی برنامه).

**چرا پلتفرم Docker و نه Next.js:** پلتفرم Next.js لیارا `npm install` و `npm run build` را اجرا می‌کند، ولی build ما پیش از آن `prisma generate` لازم دارد، که یعنی تغییر `package.json` مشترک. `Dockerfile` خود ما در CI ساخته و آزمایش می‌شود (`docker.yml`) و اگر روزی میزبان عوض شد، همان روی آروان هم اجرا می‌شود.

**بسته:** برنامه و دیتابیس هر دو دست‌کم **نقره‌ای**. بستهٔ برنزی نه انتشار بدون قطعی دارد و نه **هیچ پشتیبان خودکاری از دیتابیس** ([بسته‌ها](https://docs.liara.ir/dbaas/details/plans/software-plans/)). نقره‌ای پشتیبان روزانه با ۷ روز نگهداری دارد؛ C2 چهارده روز می‌خواهد، پس یا طلایی (هفتگی ۴ هفته) یا پشتیبان اضافه در C2.

**هزینهٔ تقریبی** (صفحهٔ قیمت لیارا، ۳ مهر ۱۴۰۵، پیش از هزینهٔ بستهٔ نقره‌ای که در صفحه نبود): برنامه ۱ گیگ/۱ CPU حدود ۱٫۳ میلیون، دیتابیس همین‌قدر، ذخیره‌ساز ۲۰ گیگ حدود ۴۷۵ هزار تومان در ماه؛ جمعاً حدود **۳٫۱ میلیون تومان در ماه به‌علاوهٔ بسته**.

**تصمیم:** _(منتظر تأیید مالک مخزن؛ تاریخ و نام را اینجا بنویسید)_

### مقادیر مخصوص لیارا
- `S3_ENDPOINT=https://storage.iran.liara.site` و `S3_REGION=default` (از [مستندات](https://docs.liara.ir/object-storage/how-tos/connect-via-platform/nextjs/)؛ اگر پنل endpoint دیگری نشان داد، همان را بگذارید).
- `TRUSTED_PROXY_HOPS=1`: همهٔ ترافیک از پراکسی معکوس لیارا می‌گذرد ([پراکسی معکوس](https://docs.liara.ir/paas/details/reverse-proxy/))، ولی اینکه `X-Forwarded-For` را **به انتها اضافه می‌کند** یا بازنویسی، و چند پراکسی جلوی برنامه است، در مستندات نیست. آزمایش بخش ۴.۳ آن را روشن می‌کند. **CDN لیارا را روشن نکنید** مگر اینکه بعدش همان آزمایش را تکرار کنید؛ هر پراکسی اضافه عدد را عوض می‌کند.
- `liara.json` در ریشهٔ مخزن: پلتفرم Docker، پورت 3000. **متغیرهای محیطی هرگز در `liara.json` نیایند**: هم رمز وارد مخزن می‌شود و هم فیلد `envs` همهٔ متغیرهای پنل را جایگزین می‌کند.
- اگر ساخت ایمیج روی سرور ایران در دریافت ایمیج Node یا بسته‌های npm گیر کرد: یا `"build": { "location": "germany" }` در `liara.json` ([liara.json](https://docs.liara.ir/paas/liarajson/))، یا آرگومان‌های `NODE_IMAGE` و `NPM_REGISTRY` در `Dockerfile` به یک mirror داخلی.

### سؤال‌هایی که باید از پشتیبانی لیارا پرسید (تیکت، پیش از انتشار اول)
1. پراکسی لیارا آدرس کاربر را به **انتهای** `X-Forwarded-For` اضافه می‌کند یا هدر را بازنویسی می‌کند؟ چند پراکسی جلوی برنامه است، با CDN و بدون آن؟
2. واحد `interval`، `timeout` و `startPeriod` در `healthCheck` میلی‌ثانیه است یا ثانیه؟ (مستندات «میلی‌ثانیه» می‌گوید، ولی نمونه‌ها شبیه ثانیه‌اند.)
3. هزینهٔ بستهٔ نقره‌ای برای برنامه و دیتابیس چقدر است؟
4. پشتیبان‌های دیتابیس کجا نگه داشته می‌شوند و می‌شود دانلودشان کرد؟ (برای C2)
5. ذخیره‌ساز نسخه‌گذاری یا کپی به منطقهٔ دیگر دارد؟ (برای C2)
6. اگر کانتینر جدید بالا نیاید (مثلاً مایگریشن شکست بخورد)، انتشار لغو می‌شود و نسخهٔ قبلی سرویس می‌دهد؟

جواب هر سؤال را همین‌جا زیر سؤال بنویسید.

## ۲. معماری پروداکشن

```
مرورگر ── HTTPS ──> پراکسی معکوس میزبان ──> برنامه (یک کانتینر، next start، پورت 3000)
                                              ├──> PostgreSQL 16 مدیریت‌شده (شبکهٔ خصوصی میزبان)
                                              ├──> ذخیره‌ساز S3: باکت public (عکس محصول، لوگو) و private (رسید)؛ هر دو خصوصی
                                              └──> کاوه‌نگار (پیامک)
```

- **فقط یک نمونه.** محدودکنندهٔ نرخ خرید و رسید در حافظهٔ همان پروسه است (`rate-limit.ts`). دو نمونه یعنی هرکدام شمارش جدا دارند و محدودیت عملاً دو برابر (سست‌تر) می‌شود؛ پیش از آن باید B10 انجام شود.
- **ایمیج:** `Dockerfile` در ریشهٔ مخزن. ساخت به دیتابیس یا رمز نیاز ندارد و همهٔ متغیرها در زمان اجرا خوانده می‌شوند، پس یک ایمیج برای staging و پروداکشن کافی است.
- **مایگریشن:** کانتینر پیش از `next start` دستور `prisma migrate deploy` را اجرا می‌کند. اگر مایگریشن شکست بخورد کانتینر بالا نمی‌آید.
- **فایل‌ها از روز اول روی S3.** پروداکشن هنوز وجود ندارد، پس هیچ فایلی روی دیسک نیست که منتقل شود و اسکریپت‌های `storage:migrate-products` و `storage:migrate-receipts` در انتشار اول لازم نیستند. (اگر روزی نسخه‌ای با `STORAGE_DRIVER=local` روی سرور اجرا شد، پیش از رفتن به S3 هر دو را طبق توضیح بالای خود اسکریپت‌ها اجرا کنید.)
- **حجم ایمیج حدود ۱٫۱۵ گیگابایت است** (اجرای `docker.yml` در PR #37)، چون همهٔ `node_modules` با وابستگی‌های توسعه در آن است تا `prisma migrate deploy` اجرا شود. اگر انتشار روی لیارا به‌خاطر حجم کند بود، `output: "standalone"` در `next.config.ts` (با هماهنگی مالکش) و نصب جداگانهٔ Prisma CLI آن را کوچک می‌کند.
- **دیسک لازم نیست.** با `STORAGE_DRIVER=s3` برنامه هیچ دادهٔ ماندگاری روی دیسک کانتینر نمی‌نویسد.

## ۳. متغیرهای محیطی

از روی [`.env.example`](../../.env.example). فقط در پنل میزبان تنظیم شوند.

| متغیر | مقدار | رمز است؟ |
|---|---|---|
| `DATABASE_URL` | رشتهٔ اتصال Postgres میزبان، با آدرس شبکهٔ خصوصی اگر میزبان دارد. `?schema=public` در انتها | بله |
| `SESSION_SECRET` | ۳۲ بایت تصادفی (دستور پایین) | بله |
| `SECRETS_KEY` | ۳۲ بایت تصادفی (دستور پایین). **یک نسخه در مدیر رمز مالک پروژه، بیرون از سرور.** بدون آن شمارهٔ کارت‌ها و اطلاعات درگاه فروشنده‌ها برای همیشه غیرقابل‌خواندن می‌شود، حتی از روی پشتیبان | بله |
| `TRUSTED_PROXY_HOPS` | تعداد پراکسی‌های جلوی برنامه (بخش ۱). اشتباهش یعنی محدودیت نرخ دور زده می‌شود یا همهٔ کاربرها یک IP حساب می‌شوند | خیر |
| `STORAGE_DRIVER` | `s3` | خیر |
| `S3_ENDPOINT`، `S3_REGION` | از پنل ذخیره‌ساز میزبان (بخش ۱) | خیر |
| `S3_ACCESS_KEY_ID`، `S3_SECRET_ACCESS_KEY` | کلید دسترسی ذخیره‌ساز، فقط برای همین دو باکت | بله |
| `S3_BUCKET_PUBLIC`، `S3_BUCKET_PRIVATE` | نام دو باکت. **هر دو خصوصی**؛ برنامه خودش فایل‌ها را سرو می‌کند | خیر |
| `KAVENEGAR_API_KEY` | از پنل کاوه‌نگار. بدون آن در پروداکشن هیچ پیامکی نمی‌رود و **هیچ‌کس نمی‌تواند وارد شود** | بله |
| `KAVENEGAR_TEMPLATE` و `KAVENEGAR_TEMPLATE_*` | نام قالب‌های تأییدشده (بخش ۶). قالبی که تنظیم نشده باشد ارسال نمی‌شود و `FAILED` ثبت می‌شود | خیر |
| `BILLING_ENABLED` | `false` تا تصمیم هفتهٔ ۶ | خیر |

`PORT` (پیش‌فرض 3000) و `NODE_ENV=production` در خود ایمیج تنظیم شده‌اند. `E2E_*` و `TEST_DATABASE_URL` هرگز روی پروداکشن تنظیم نشوند.

ساخت کلید تصادفی (روی کامپیوتر خودتان، و مستقیم در پنل میزبان و مدیر رمز بگذارید):

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

**عوض کردن کلیدها:** تغییر `SESSION_SECRET` همهٔ کاربرها را از حساب بیرون می‌کند و کدهای ورودِ در راه را باطل می‌کند (اشکالی ندارد). `SECRETS_KEY` را **هرگز** عوض نکنید مگر با رمزنگاری دوبارهٔ داده‌ها.

## ۴. انتشار از صفر

پیش از شروع یک Issue با عنوان «انتشار اول پروداکشن» باز کنید و هر مرحله را آنجا تیک بزنید. پیش‌نیاز: الگوی `LOGIN_OTP` کاوه‌نگار **تأیید شده باشد** (بخش ۶)؛ بدون آن هیچ‌کس روی پروداکشن نمی‌تواند وارد شود.

### ۴.۱ ساختن منابع (پنل لیارا، حساب مالک پروژه)
1. **کیف پول** را شارژ کنید.
2. **دیتابیس:** PostgreSQL، آخرین نسخهٔ **۱۶**، بستهٔ نقره‌ای یا طلایی (بخش ۱). دسترسی عمومی را **خاموش** کنید. آدرس اتصال **شبکهٔ خصوصی** را بردارید و آخرش `?schema=public` بگذارید؛ این `DATABASE_URL` است.
3. **ذخیره‌ساز:** دو باکت **خصوصی**، مثلاً `ghaltak-public` و `ghaltak-private` (اگر نام گرفته شده بود، یک پسوند اضافه کنید). یک کلید دسترسی بسازید که فقط به همین دو باکت دسترسی دارد.
4. **برنامه:** پلتفرم **Docker**، بستهٔ نقره‌ای یا طلایی، ۱ گیگ رم و ۱ CPU. نامش را همان مقدار `app` در `liara.json` بگذارید (اگر گرفته شده بود، هر دو را با هم عوض کنید). همهٔ متغیرهای بخش ۳ را در بخش «متغیرها»ی برنامه وارد کنید.

### ۴.۲ انتشار
از یک کامپیوتر با آخرین `main` (بدون تغییر محلی):

```bash
git switch main && git pull
git status              # باید تمیز باشد
npm install -g @liara/cli
liara login
liara deploy            # liara.json را می‌خواند: پلتفرم Docker، پورت 3000
```

در لاگ انتشار باید اجرای مایگریشن‌ها (`migrate deploy`) و بعد `Ready` از Next.js دیده شود. شناسهٔ commit منتشرشده (`git rev-parse --short HEAD`) را در Issue بنویسید.

بعد:
1. **دامنه:** دامنه را در پنل برنامه اضافه کنید، رکوردهای DNS را طبق پنل بگذارید، و SSL را روشن کنید. `https://<دامنه>/api/health` باید `{"ok":true}` بدهد.
2. **بررسی سلامت:** بعد از جواب سؤال ۲ پشتیبانی، `healthCheck` با آدرس `/api/health` در `liara.json` اضافه شود. تا آن موقع `HEALTHCHECK` خود `Dockerfile` هست.
3. **لاگ:** لاگ‌های برنامه در بخش «لاگ‌ها»ی پنل است (stdout کانتینر). هیچ سرویس لاگ خارجی اضافه نشود (قانون ۷).

### ۴.۳ آزمایش پراکسی و محدودیت نرخ
محدودیت ارسال رسید ۵ بار در ۱۰ دقیقه برای هر IP است و **پیش از** پیدا کردن سفارش بررسی می‌شود (`payment-actions.ts`). پس تکرار یک درخواست ارسال رسید روی سفارشی که قبلاً پرداخت شده هیچ اثری ندارد جز شمردن.

**بخش الف: هدر جعلی محدودیت را دور نمی‌زند**
1. به‌عنوان فروشنده یک محصول و لینک خرید بسازید. لینک را روی **لپ‌تاپ** باز کنید و سفارش بدهید.
2. در صفحهٔ سفارش، DevTools (F12) را باز کنید و در تب Network یک تصویر کوچک به‌عنوان رسید بفرستید. روی درخواست POST به `/buy/order/...` راست‌کلیک کنید: **Copy > Copy as cURL (bash)**.
3. به‌عنوان فروشنده پرداخت همان سفارش را تأیید کنید.
4. در Git Bash، به‌جای `<cURL>` دستور کپی‌شده را بگذارید:

   ```bash
   for i in 1 2 3 4 5 6 7; do
     <cURL> -s -H "X-Forwarded-For: 203.0.113.$i" | grep -o "زیاد است\|ثبت شده" | head -1
   done
   ```

   **درست:** چند جواب اول «ثبت شده» (سفارش قبلاً پرداخت شده) و از ششمین درخواست به بعد، با احتساب ارسال مرحلهٔ ۲، «زیاد است».
   **خطا:** هر هفت جواب «ثبت شده». یعنی IP جعلی پذیرفته شده و محدودیت دور زده می‌شود. انتشار را برای مشتری‌ها باز نکنید؛ `TRUSTED_PROXY_HOPS` یا پراکسی را درست کنید و دوباره آزمایش کنید.

**بخش ب: کاربرهای مختلف یک IP حساب نمی‌شوند**
همان لحظه (پیش از گذشتن ۱۰ دقیقه) با **گوشی روی اینترنت همراه**، نه وای‌فای همان لپ‌تاپ، یک سفارش تازه از لینک بدهید و رسید بفرستید. **باید پذیرفته شود.** اگر «زیاد است» گرفتید، برنامه IP پراکسی را به‌جای IP کاربر می‌بیند و همهٔ مشتری‌ها یک محدودیت مشترک دارند: `TRUSTED_PROXY_HOPS` بیش از حد است، یا یک پراکسی اضافه (مثلاً CDN) جلوی برنامه است.

نتیجهٔ هر دو بخش را در Issue انتشار بنویسید. بعد از هر تغییر در پراکسی، CDN یا `TRUSTED_PROXY_HOPS` این آزمایش تکرار شود.

### ۴.۴ انجام‌شده وقتی (C1)
- [ ] یک فروشنده با کد پیامکی واقعی وارد شد و محصولی با عکس ساخت (عکس از S3 سرو می‌شود).
- [ ] یک مشتری با گوشی از لینک خرید سفارش داد.
- [ ] آزمایش ۴.۳ (الف و ب) پاس شد.
- [ ] `/api/health` به بررسی سلامت لیارا وصل است.
- [ ] یک نفر دیگر از تیم فقط با همین فایل یک انتشار انجام داد (بخش ۵)، و هر جایی که گیر کرد اینجا درست شد.

## ۵. هر انتشار: چک‌لیست

این چک‌لیست را در توضیح PR یا Issue انتشار کپی کنید و تیک بزنید.

**پیش از انتشار**
- [ ] CI روی `main` سبز است (یا اگر CI متوقف است، بخش ۷.۵ رعایت شده).
- [ ] مایگریشن جدید دارد؟ فهرست `prisma/migrations` را با نسخهٔ در حال اجرا مقایسه کنید. اگر دارد:
  - [ ] با نسخهٔ **قبلی** برنامه هم سازگار است؟ (مثلاً ستون جدید nullable یا با پیش‌فرض است، و ستونی حذف یا تغییر نام نمی‌شود که نسخهٔ قبلی هنوز می‌خواند.) اگر نه، دو انتشار لازم است: اول افزودن، بعد حذف.
  - [ ] یک پشتیبان دستی از دیتابیس گرفته شد (پنل دیتابیس لیارا؛ جزئیات در C2).
- [ ] متغیر محیطی جدید لازم است؟ `git diff <نسخهٔ قبلی>..main -- .env.example` را ببینید و **پیش از** انتشار در پنل تنظیم کنید.
- [ ] اسکریپت یک‌باره‌ای (`scripts/`) لازم است؟ در توضیح PRها نوشته شده است.
- [ ] شناسهٔ commit فعلی پروداکشن یادداشت شد (برای برگشت).

**انتشار:** `liara deploy` از روی `main` تمیز، طبق بخش ۴.۲.

**بعد از انتشار** (حدود ۵ دقیقه)
- [ ] لاگ کانتینر: `migrate deploy` بدون خطا و `Ready` از Next.js.
- [ ] `https://<دامنه>/api/health` جواب `{"ok":true}` می‌دهد.
- [ ] ورود با کد پیامکی واقعی.
- [ ] یک لینک خرید روی گوشی باز می‌شود و عکس محصول دیده می‌شود.
- [ ] اگر تغییر به پیامک یا پرداخت مربوط است، همان مسیر یک بار واقعی امتحان شد.

**برگشت به نسخهٔ قبل**
- **بدون مایگریشن:** نسخهٔ قبلی را دوباره منتشر کنید: `git switch --detach <commit یادداشت‌شده>` و بعد `liara deploy`. چون ایمیج به دیتابیس وابسته نیست، این کافی است. بعد `git switch main`.
- **با مایگریشن:** Prisma مایگریشن را خودکار برنمی‌گرداند. اگر مایگریشن با نسخهٔ قبلی سازگار بوده (قاعدهٔ بالا)، فقط نسخهٔ قبلی را منتشر کنید و مایگریشن در دیتابیس بماند. (مستندات Prisma نمی‌گوید `migrate deploy` نسخهٔ قبلی با دیتابیسی که یک مایگریشنِ ناشناخته دارد چه می‌کند؛ این را یک بار روی یک دیتابیس آزمایشی امتحان کنید و نتیجه را اینجا بنویسید.) اگر نبوده، دیتابیس را از پشتیبانِ پیش از انتشار بازیابی کنید (C2) و بعد نسخهٔ قبلی را منتشر کنید؛ سفارش‌های بین این دو از دست می‌روند، پس اول در Issue ثبت و با تیم هماهنگ شود.

## ۶. پیامک: کاوه‌نگار

### حساب
1. حساب کاوه‌نگار به نام مالک پروژه (نه یک عضو تیم)، با احراز هویت کامل. ایمیل و موبایل بازیابی مال مالک باشد.
2. کلید API را از پنل بسازید و مستقیم در پنل میزبان بگذارید (`KAVENEGAR_API_KEY`). اگر پنل محدود کردن کلید به IP را دارد، آن را به IP خروجی سرور محدود کنید.
3. اعتبار اولیه برای آزمایش و حدود یک ماه پیامک فروشنده‌های آزمایشی شارژ شود. یادآوری کم شدن اعتبار در پنل روشن شود.

### قالب‌ها
برنامه با **الگو** (verify/lookup) پیامک می‌فرستد ([مستندات](https://kavenegar.com/rest.html)): متن ثابت الگو در [پنل](https://console.kavenegar.com/verification) ثبت می‌شود، کارشناس کاوه‌نگار تأییدش می‌کند، و برنامه فقط مقدار `%token`، `%token2` و `%token3` را می‌فرستد. قواعد توکن: ۱ تا ۱۰۰ نویسه و **بدون فاصله**؛ `src/server/sms/providers.ts` فاصله را به نیم‌فاصله تبدیل می‌کند. الگوی تأییدنشده خطای 424 می‌دهد.

**متن الگو بعد از تأیید ثابت است** و ترتیب توکن‌ها قرارداد بین این فایل و کدی است که پیامک را می‌فرستد. هر تغییری یعنی تأیید دوباره، پس پیش از ثبت، صاحب هر ردیف (ستون «فرستنده») ترتیب را تأیید کند.

پیش از ثبت، `<دامنه>` را با دامنهٔ پروداکشن (بخش ۱) جایگزین کنید.

| نوع (`SmsKind`) | متغیر محیطی | فرستنده | توکن‌ها | وضعیت |
|---|---|---|---|---|
| `LOGIN_OTP` | `KAVENEGAR_TEMPLATE` | A (`otp.ts`، فعال) | `%token`: کد ۶ رقمی | ثبت نشده |
| `ORDER_PLACED` | `KAVENEGAR_TEMPLATE_ORDER_PLACED` | B (B7) | `%token`: کد سفارش، `%token2`: لینک صفحهٔ سفارش | ثبت نشده |

| `ORDER_SHIPPED` | `KAVENEGAR_TEMPLATE_ORDER_SHIPPED` | B (B7) | `%token`: کد سفارش، `%token2`: کد رهگیری، `%token3`: لینک صفحهٔ سفارش | ثبت نشده |

## ۷. CI

### ۷.۱ چرا مهم است
مخزن خصوصی است، پس هر اجرای GitHub Actions از سهمیهٔ حساب **مالک مخزن** کم می‌شود: [۲۰۰۰ دقیقه در ماه برای GitHub Free و ۳۰۰۰ برای Pro](https://docs.github.com/en/billing/concepts/product-billing/github-actions)، که اول هر ماه صفر می‌شود. گیت‌هاب [هر job را جدا به دقیقهٔ کامل رو به بالا گرد می‌کند](https://docs.github.com/en/billing/reference/actions-runner-pricing). وقتی سهمیه تمام شود و روش پرداختی ثبت نشده باشد، همهٔ اجراها متوقف می‌شوند. در ۳ مهر ۱۴۰۵ اجراها چند ساعت به‌خاطر مشکل پرداخت یا سقف هزینهٔ حساب مالک متوقف شدند؛ این مخزن تا آن روز فقط حدود ۱۸۵ دقیقه مصرف کرده بود، پس علت یا مخزن‌های دیگر مالک بوده یا خود تنظیم پرداخت. مالک در Settings > Billing بررسی کند.

### ۷.۲ چه کردیم و چقدر کم شد
اندازه‌گیری از روی ۶۵ اجرای ۲ و ۳ مهر (زمان هر job از API گیت‌هاب):

| | پیش از C3 | بعد از C3 |
|---|---|---|
| jobها در هر اجرا | ۲ (`check`، `e2e`) | ۱ |
| زمان هر job (میانه) | `check` ۱٫۳ و `e2e` ۱٫۸ دقیقه | ۱٫۵ دقیقه (۸۸ ثانیه، اجرای PR #37) |
| دقیقهٔ حساب‌شده در هر اجرا (میانه) | ۴ | ۲ |
| مصرف ۲ روز کاری | ۱۷۵ دقیقه، یعنی با این سرعت حدود ۲۶۰۰ در ماه، بیش از سهمیهٔ Free | با همان تعداد اجرا نصف، و کمتر چون اجراهای کهنه لغو و PRهای مستندات رد می‌شوند |

تغییرها در `.github/workflows/ci.yml`:
1. **یک job به‌جای دو:** راه‌اندازی (checkout، `npm ci`، دیتابیس) دو بار پرداخت می‌شد و هر job جدا گرد می‌شد. زمان واقعی کمی بیشتر می‌شود، دقیقهٔ حساب‌شده کمتر.
2. **PostgreSQL خود runner** به‌جای کانتینر سرویس: حدود ۲ ثانیه به‌جای ۱۵ تا ۲۰. runner روی `ubuntu-24.04` ثابت است چون Postgres آن [نسخهٔ ۱۶](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md) است، همان نسخهٔ پروداکشن.
3. **Google Chrome خود runner** برای e2e (`E2E_BROWSER_CHANNEL=chrome` در `playwright.config.ts`) به‌جای دانلود Chromium و کتابخانه‌هایش در هر اجرا (حدود ۲۵ ثانیه).
4. **لغو اجرای کهنه:** push جدید به همان PR اجرای قبلی را لغو می‌کند.
5. **PRهای فقط مستندات** (`*.md` و `docs/`) CI اجرا نمی‌کنند.
6. **`timeout-minutes: 15`:** پیش‌فرض گیت‌هاب ۶ ساعت است؛ یک تست گیرکرده (مثل بن‌بستی که در A5 پیدا شد) می‌توانست ۳۶۰ دقیقه بسوزاند.

کش npm از قبل فعال بود. کش `.next/cache` فعلاً اضافه نشد: build فقط حدود ۱۵ ثانیه است و ذخیره و بازیابی کش هم وقت می‌گیرد. اگر build بزرگ‌تر شد، دوباره بررسی شود ([راهنمای Next.js](../../node_modules/next/dist/docs/01-app/02-guides/ci-build-caching.md)).

`docker.yml` ایمیج پروداکشن را می‌سازد و بررسی می‌کند که بالا بیاید، اما **فقط** وقتی فایلی عوض شود که ایمیج را شکل می‌دهد (`Dockerfile`، `package-lock.json`، `next.config.ts` و ...).

### ۷.۳ پایش هفتگی
- `ci-usage.yml` هر شنبه ساعت ۸ صبح به وقت تهران اجرا می‌شود (و دستی از تب Actions با «Run workflow»). مصرف این ماه، سرعت هفتهٔ اخیر و پیش‌بینی آخر ماه را در صفحهٔ همان اجرا نشان می‌دهد.
- اگر پیش‌بینی از ۷۰٪ سهمیه بگذرد، یک Issue با عنوان «CI minutes: on track to pass the monthly quota» باز می‌کند (یا روی Issue باز قبلی کامنت می‌گذارد).
- این عدد **فقط همین مخزن** است. مخزن‌های خصوصی دیگر مالک از همان سهمیه مصرف می‌کنند؛ عدد واقعی در Settings > Billing حساب مالک است. مالک هر هفته آن را هم نگاه کند.

### ۷.۴ اگر سهمیه رو به اتمام است
با مالک مخزن **از قبل** یکی را انتخاب کنید و تصمیم را همین‌جا بنویسید:
- **روش پرداخت و سقف هزینه** روی حساب مالک: Actions بعد از سهمیه ادامه می‌دهد و فقط اضافه‌اش پولی است ([قیمت‌ها](https://docs.github.com/en/billing/reference/actions-runner-pricing)). سقف هزینه جلوی خرج غیرمنتظره را می‌گیرد.
- **GitHub Pro** برای مالک: ۳۰۰۰ دقیقه، و محافظت از برنچ `main` هم ممکن می‌شود (مشکل باز فاز ۱).
- **عمومی کردن مخزن:** Actions رایگان و محافظت از برنچ ممکن می‌شود، ولی کد عمومی می‌شود. پیش از آن باید مطمئن شد هیچ رمزی در تاریخچهٔ git نیست.

**تصمیم:** _(ثبت نشده)_

### ۷.۵ اگر CI متوقف شد
PR فقط وقتی مرج شود که نویسنده‌اش این‌ها را روی کامپیوتر خودش اجرا کرده و خروجی خلاصه را در PR گذاشته باشد:

```bash
npm run lint
npm run typecheck
npm test            # با TEST_DATABASE_URL، تا تست‌های دیتابیس هم اجرا شوند (docs/phase1/README.md)

```

بعد از برگشتن CI، روی `main` یک اجرای دستی بگیرید: تب Actions، workflow «CI»، دکمهٔ «Run workflow» با برنچ `main`. هر مشکلی که پیدا شد، یک Issue برای PR مرج‌شده‌ای که آن را آورده.
